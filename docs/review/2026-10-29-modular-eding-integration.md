# Eding modular integration — local review

The existing eding.dev homepage is live and its source/hosting was not established by this work. `hub/` is a generated project-directory proposal; it has not replaced the apex site. `shared/eding/projects.json` is its catalog; `pipeline/sync_shared.py` regenerates the directory and ECERankings token copy. ECERankings has an Eding link, framework-independent tokens, `npm run check`, a reusable validation workflow, and a generated `dist/version.json` containing the data manifest hash. The build packages the previously validated data and does not fetch or refresh it.

Scribe changes are in the separate, uncommitted checkout `.tmp/eding-modular-work`, at its fetched `main` revision. It contains the pinned identity token copy, an Eding link, expanded existing version metadata, and its own validation workflow. The repo is a scratch checkout, not the user's canonical local checkout. No project was committed, pushed or deployed by this integration.

The shared package is currently a local versioned contract, not a published npm package. The Scribe token copy must be updated deliberately. Cross-repo workflow reuse depends on publishing a stable reference and access permissions; the Scribe workflow is independent until then. To complete the plan, establish the apex homepage source, integrate the generated catalog there, release the shared package or adopt a reliable pinned distribution, link Scribe to a published reusable workflow, review both repository diffs, and deploy the projects. Dataset snapshot publication/versioning beyond the existing manifest is still a future improvement; it has not been separated into its own distribution channel.

ECERankings `version.json` has a nullable dirty flag when sandbox permissions prevent git status. The source revision is the git baseline, and a dirty flag of null is unknown, not clean. The dataset hash covers the validated data manifest, whose own hashes cover its artifacts; generation time is not a coverage guarantee.
